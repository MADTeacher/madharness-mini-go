# Слой контекста

Слой контекста отвечает за то, какие сообщения модель видит в `ask` и `run`.
Он живёт в пакете `internal/agentcontext` и не зависит от политики безопасности,
HTTP-клиента модели или handlers инструментов. Внешний код передаёт ему готовые
тексты и события, а на выходе получает список `messages` для OpenAI-совместимого
Chat Completions API.

`messages` — это ровно тот список сообщений, который harness отправляет в поле
`messages` HTTP-запроса к модели: системные правила, задача пользователя, ответы
assistant и результаты инструментов.

## Основные типы

`Fragment` описывает отдельный кусок контекста: системный prompt, проектные
инструкции или другой учебный фрагмент, который должен попасть в запрос к
модели. У фрагмента есть `ID`, `Source`, `Text`, `Priority`, `Placement` и
`Transient`.

`Provider` — простой интерфейс для дополнительных источников контекста. Provider
получает `State` и возвращает дополнительные `Fragment`, не импортируя
`internal/agent`, `internal/model` или `internal/tools`.

`Manager` хранит задачу пользователя, закреплённые фрагменты и историю
assistant/tool сообщений. Основной метод `Messages()` возвращает готовый список
сообщений для модели, а `Stats()` показывает примерную токеновую оценку
собранного контекста и факт обрезки.

`Report()` возвращает более подробный Context Report для трасс и отладки. Он
показывает токеновую оценку до и после бюджетной обработки, список фрагментов с
их источниками и размерами, количество элементов истории, обрезанные tool
messages и удалённые старые элементы истории. Сам текст prompt и tool output в
отчёт не попадает, чтобы трасса оставалась компактной и не дублировала
чувствительный контент.

## Как используется в `run`

`agent.Run()` создаёт `Manager` через `agentcontext.BaseContext()`, читает
встроенный prompt и `AGENTS.md`, затем добавляет их как закреплённые фрагменты.

Закреплённый фрагмент — это часть контекста, которую нельзя удалить при обрезке
старой истории. Например, системный prompt и правила проекта должны оставаться
видимыми модели даже тогда, когда результаты старых инструментов уже не влезают
в бюджет контекста.

После каждого ответа модели общий цикл вызывает `RecordAssistant()`. Если
модель запросила инструмент, результат записывается через `RecordToolResult()`.
Сообщение assistant с `tool_calls` и соответствующие `role=tool` ответы
хранятся как атомарный элемент истории: при обрезке они сохраняются или
удаляются вместе.

Перед сохранением assistant-сообщение нормализуется: в историю попадают только
поля, которые нужны следующему Chat Completions запросу (`role`, `content`,
`tool_calls`). Vendor-specific поля вроде `reasoning`, `reasoning_details`,
`refusal` и другие диагностические блоки не отправляются модели повторно.
Длинный assistant `content` укорачивается с пометкой `context clipped`, чтобы
модель не платила за собственные длинные рассуждения на каждом следующем ходе.

Мультимодальные follow-up сообщения, например вложение из `read_image`,
добавляются после закрытия всех `tool_calls`. Observation инструмента остаётся
текстовым JSON без base64, поэтому трасса не раздувается изображениями.

## Бюджет контекста

Harness задаёт бюджет контекста в токенах через `context_max_tokens`, но не
использует tokenizer конкретной модели. OpenAI-совместимый API может вести к
разным провайдерам и моделям, поэтому слой контекста считает консервативную
оценку: сериализует отправляемые данные в компактный JSON, смотрит размер в
байтах и делит его на фиксированную цену токена.

Эта оценка не совпадает с точным счётчиком провайдера, зато работает одинаково
для разных моделей и не требует новых зависимостей. В режиме `run` в бюджет
входят не только `messages`, но и схемы доступных tools, потому что они тоже
отправляются модели при каждом вызове.

| Поле | Значение по умолчанию | Смысл |
| --- | --- | --- |
| `context_max_tokens` | `60000` | Примерный максимум токенов запроса к модели. |
| `context_keep_recent_turns` | `3` | Сколько последних элементов истории желательно сохранить при удалении старых. |

Закреплённые фрагменты и исходная задача пользователя не удаляются. Если контекст
слишком большой, сначала укорачиваются `role=tool` outputs с явной пометкой
`context clipped`. Если этого мало, старые неприкреплённые элементы истории
удаляются целиком.

`context_keep_recent_turns` — это предпочтение, а не разрешение превысить
бюджет. Если сохранённые недавние элементы всё ещё не помещаются, `Manager`
принудительно удаляет и их. Если даже после этого базовый запрос со схемами
tools остаётся больше `context_max_tokens`, harness завершает ход с ошибкой
`context budget exceeded after truncation` вместо отправки заведомо слишком
большого запроса к модели.

## Расширение инструментов и контекста

Инструменты расширяются через `tools.Provider`, а контекст — через
`agentcontext.Provider`. Даже в этой ветке полезно видеть, что это две
независимые точки подключения:

- `tools.Provider.Specs(ctx)` отдаёт `tools.Spec` для вызова модели.
- `agentcontext.Provider.Collect(state)` отдаёт инструкции или другие
  фрагменты, которые модель должна видеть перед вызовом инструмента.

Так инструмент может появиться без правки агентского цикла, а контекстные
инструкции не смешиваются с кодом выполнения handlers.
