# Дорожная карта рефакторинга

Этот документ фиксирует задачи, которые не входят в первую волну точечных
исправлений после ревью. Они отложены не потому, что не важны, а потому что
пересекаются с несколькими пакетами или требуют отдельного архитектурного
решения.

## После первой волны

### Redaction trace-событий

Сейчас первая волна закрывает прямые утечки через shell, hooks и отдельные
инструменты. Следующий шаг - единый слой редактирования trace payload перед
записью JSONL.

Нужно проверить и закрыть события:

- `model_call_finished`;
- `approval_request` и `approval_decision`;
- `tool_observation`;
- `process_output`.

Готовность: секреты вроде API-ключей, bearer-токенов, паролей и похожих
значений не появляются в JSONL trace, даже если модель передала их в tool args
или subprocess напечатал их в stdout/stderr.

### Единая redaction-политика

Hooks уже получают compact/redacted payload, а trace пока пишет более сырые
данные. После исправления trace стоит убрать расхождение между этими слоями:
одинаковые ключи и строки должны редактироваться одинаково.

Готовность: tests для hooks и trace используют общий набор примеров секретов, а
изменение redaction-правила не требует править две независимые реализации.

### Fairness workspace scheduler

Текущий scheduler смотрит только на активные locks. При постоянном потоке чтений
ожидающая запись или exclusive-операция может ждать слишком долго.

Готовность: если write/exclusive lock уже ждёт, новые конфликтующие read locks
не обходят его бесконечно; тест фиксирует порядок `read -> pending write ->
next read`.

### Строгая модель shell-команд

Первая волна усиливает denylist и обработку очевидных wrapper/interpreter
обходов. Отдельно стоит решить, должна ли shell policy перейти от эвристик к
более строгой модели разрешённых команд.

Возможные направления:

- allowlist безопасных команд для учебного режима;
- отдельная policy для команд чтения, тестов и dev-серверов;
- явные профили shell-доступа для parent agent и субагентов.

Готовность: shell-политика описана в документации, покрыта тестами на обходы и
не зависит от случайного распознавания одного первого argv.

## Общие проверки

После каждой будущей волны нужно запускать:

```bash
GOMODCACHE=$PWD/.go-mod-cache GOCACHE=$PWD/.go-build-cache go test ./...
GOMODCACHE=$PWD/.go-mod-cache GOCACHE=$PWD/.go-build-cache go vet ./...
GOMODCACHE=$PWD/.go-mod-cache GOCACHE=$PWD/.go-build-cache go test -race ./...
```

Если sandbox мешает tests, которым нужен localhost или subprocess lifecycle,
проверку нужно повторить без sandbox-ограничений и явно отметить это в отчёте.
