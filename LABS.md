# Лабораторные работы: 03-Context-Layer

Эта ветка тренирует контекстную инженерию внутри harness: что именно модель
видит перед вызовом, как хранится история assistant/tool сообщений, как
оценивается бюджет запроса и что происходит, когда контекст становится слишком
большим.

Ключевая архитектурная граница ветки — пакет `internal/agentcontext`. Он не
вызывает модель, не проверяет пути и не исполняет инструменты. Его задача:
получить готовые фрагменты, задачу и историю, собрать `messages`, применить
бюджет и объяснить результат через `context_report`.

## Базовый уровень

### 1. Расширить `context_report` составом фрагментов

Контекст проблемы: `Manager.Report()` показывает отдельные фрагменты контекста,
но общую картину приходится собирать вручную. При этом встроенный system prompt
и `AGENTS.md` должны оставаться различимыми по источнику, хотя в запросе к
модели они рендерятся в одно `role=system` сообщение.

Индустриальный ориентир: в зрелых harness контекст имеет явное происхождение.
Трасса показывает не содержимое инструкций, а то, из каких источников они пришли
и в какую часть запроса попали.

Задание: добавьте в `context_report` агрегированную сводку по фрагментам:
сколько всего фрагментов собрано, сколько попало в `system` и `user`, сколько
временных provider-фрагментов помечено `Transient=true`, общий размер
фрагментов в символах и список источников без полного текста.

Ограничения:

- не записывать полный system prompt или текст `AGENTS.md` в trace;
- сохранить существующий список `fragments` в отчёте;
- не менять формат Chat Completions `messages`;
- не переносить в эту задачу вложенные `AGENTS.md`.

Критерий готовности: `context_report` показывает и подробные элементы, и
компактную сводку. В отчёте отдельно видны встроенный system prompt и корневой
`AGENTS.md`, но их тексты не попадают в trace.

Проверка: создать `Manager` с system-фрагментом, фрагментом `AGENTS.md`,
user-фрагментом и временным provider-фрагментом; проверить, что `Report()`
считает их отдельно, показывает sources и не содержит полного текста.

### 2. Сделать ошибку переполнения контекста обучающей

Контекст проблемы: harness должен остановить слишком большой запрос до API, но
пользователю важно понять, какая часть запроса съела бюджет: сообщения, схемы
инструментов или история.

Индустриальный ориентир: ошибка бюджета должна быть структурированной
диагностикой. Она не раскрывает содержимое запроса, но показывает оценки и
настройки, которые влияют на ситуацию.

Задание: расширьте ошибку `context budget exceeded after truncation`, чтобы в
ней были `request_tokens_estimate`, `messages_tokens_estimate`,
`tools_tokens_estimate`, `max_tokens`, число обрезанных tool messages и число
удалённых history entries. Сообщение должно подсказывать, что можно менять:
`context_max_tokens`, `context_keep_recent_turns`, длину задачи, объём tool
output или набор доступных tools.

Ограничения:

- не отправлять заведомо слишком большой запрос модели;
- не скрывать сам факт ошибки;
- не выводить содержимое prompt или tool output;
- сохранить событие `context_error` в trace.

Критерий готовности: по CLI-ошибке понятно, какая часть запроса переполнила
бюджет и какие настройки относятся к проблеме.

Проверка: в тесте задать очень маленький `context_max_tokens` и большую схему
инструмента; убедиться, что ошибка содержит оценки и подсказки, а trace содержит
безопасный `context_report`.

## Основной уровень

### 1. Добавить CLI-команду для предварительного просмотра контекста

Контекст проблемы: сейчас оценку будущего запроса можно увидеть только после
обращения к модели и чтения JSONL-трассы. Для учебного harness полезно заранее
сравнить стоимость `ask` и `run`.

Индустриальный ориентир: предварительная проверка запроса не должна смешиваться
с обращением к модели или выполнением инструментов. Пользователь видит бюджет
до запуска и может изменить настройки до дорогого model call.

Задание: добавьте CLI-команду `go run ./cmd/madharness-mini context "задача"`.
Она должна строить `agentcontext.Manager` так же, как `ask` или `run`, но не
вызывать LLM. Команда показывает estimates для messages, tools и всего request,
`context_max_tokens`, список источников фрагментов и факт `over_budget`.

Для режима `run` команда должна учитывать schemas доступных tools, потому что
они тоже занимают контекст. Используйте флаг `--mode ask|run`, где `ask` —
значение по умолчанию.

Ограничения:

- команда не должна обращаться к модели;
- не печатать полный system prompt или `AGENTS.md`;
- не выполнять tools;
- вывод должен быть стабильным для CLI-теста.

Критерий готовности: можно сравнить `ask` и `run` для одной задачи и увидеть,
почему `run` дороже по бюджету из-за tool schemas.

Проверка: запустить preview в тестовом проекте с `AGENTS.md`; проверить, что
`--mode ask` показывает `tools_tokens_estimate=0`, а `--mode run` показывает
ненулевую стоимость tools.

### 2. Сделать бюджетные действия отдельными событиями trace

Контекст проблемы: clipping tool output и удаление старой истории видны внутри
`context_report`, который лежит в `model_call_started`. Этого достаточно для
снимка состояния, но плохо показывает последовательность решений слоя
контекста.

Индустриальный ориентир: trace должен быть журналом решений, а не только
последним снимком. В зрелых системах такие события нужны для аудита, регрессий и
объяснения поведения агента на длинных сессиях.

Задание: добавьте отдельные trace-события, например
`context_tool_output_clipped`, `context_history_dropped` и
`context_hard_limit_exceeded`. По JSONL должно быть видно, какие действия были
применены перед model call.

События должны появляться одинаково для `ask` и `run`, если соответствующее
действие произошло. Не дублируйте логику в двух режимах: пусть сборка контекста
возвращает явный результат бюджетных действий или используйте общий helper.

Ограничения:

- не дублировать большой tool output;
- не писать полный prompt;
- события должны появляться только когда действие реально произошло;
- сохранить текущий `context_report`.

Критерий готовности: trace показывает не только финальную сводку, но и
отдельные факты: что было обрезано, что было удалено и на каком ходе.

Проверка: смоделировать `run` с большим результатом `read_file` или `run_shell`
и малым бюджетом; убедиться, что в trace появились события clipping и, при
необходимости, удаления старой истории. Отдельно проверить `ask` со слишком
большим стартовым контекстом, чтобы `context_hard_limit_exceeded` и
`context_error` оставались согласованными.

## Продвинутый уровень

### 1. Суммаризировать удаляемую историю через модель

Контекст проблемы: сейчас старые `HistoryEntry` при нехватке бюджета удаляются
целиком. Это просто и предсказуемо, но на длинной сессии агент теряет рабочую
память: какие действия уже были выполнены, какие файлы затрагивались и какие
выводы важны для продолжения.

Индустриальный ориентир: это упрощённое сжатие рабочей памяти. Слой контекста
решает, какие элементы не помещаются, но не должен сам становиться клиентом
модели: LLM-вызов для summary должен жить на границе агентского цикла или в
явно переданном summarizer-интерфейсе.

Задание: добавьте механизм суммаризации истории перед удалением. Когда контекст
не помещается, harness выбирает старые элементы истории, отправляет их модели
отдельным коротким запросом без tools, а затем заменяет исходные тяжёлые
сообщения компактным служебным фрагментом.

Не импортируйте `model.Client` внутрь `agentcontext.Manager`. Один приемлемый
вариант: `Manager` возвращает кандидатов на сжатие, а model/tool loop вызывает
отдельный `HistorySummarizer` и передаёт обратно готовое summary. Другой вариант
— явный callback, который можно подменить fake model client в тесте.

Ограничения:

- summary-запрос должен быть коротким и не использовать tools;
- `Manager` не должен зависеть от HTTP-слоя;
- полная исходная история должна оставаться в JSONL trace;
- summary должно быть явно помечено как сжатая история, а не как новое
  пользовательское сообщение;
- если summary тоже не помещается, жёсткий бюджет важнее;
- trace должен показывать, что история была суммаризирована, какие entries
  заменены и сколько символов удалось сэкономить.

Критерий готовности: при длинной сессии старые tool turns заменяются
model-generated summary, и последующие вызовы модели продолжают работу,
опираясь на это резюме вместо полного старого контекста.

Проверка: создать fake model client для summary-запроса, несколько старых tool
turns и маленький бюджет. Проверить, что следующий `messages` содержит summary,
не содержит длинный stdout, а trace фиксирует событие суммаризации. В
исследовательской части сравнить тот же сценарий без summary и с summary:
сколько токенов удалось сэкономить и какая информация потерялась.

### 2. Спроектировать priority-aware eviction для истории

Контекст проблемы: `Fragment.Priority` влияет на порядок фрагментов, но история
удаляется в основном по возрасту. Иногда старое наблюдение инструмента важнее
нового короткого ответа, и простая стратегия «удаляем самое старое» становится
слишком грубой.

Индустриальный ориентир: это policy-based eviction. История удаляется не только
по возрасту, а по явной политике, где важность, свежесть и жёсткий бюджет
разведены как разные факторы.

Задание: добавьте приоритеты для элементов истории или tool observations, чтобы
важные результаты можно было сохранять дольше обычных. Один простой вариант:
у `HistoryEntry` появляется `Priority` со значением по умолчанию `100`, меньшее
число означает более важную историю, а равные приоритеты удаляются по возрасту.

Источник приоритета тоже должен быть явным: параметр
`RecordAssistant()`/`RecordToolResult()` или metadata-поле observation, которое
не утекает в `role=tool` content для модели.

Ограничения:

- приоритет не должен позволять превысить жёсткий бюджет;
- assistant/tool пара должна оставаться атомарной;
- metadata приоритета не должна попадать в content для модели;
- поведение должно быть видно в `context_report`;
- старые тесты бюджета должны остаться осмысленными.

Критерий готовности: на маленьком сценарии видно, что низкоприоритетная история
удаляется раньше, а важная сохраняется до тех пор, пока это совместимо с
бюджетом. В `context_report` видно, какой priority был у включённых и удалённых
entries и почему правило разрешения равенства выбрало именно их.

Проверка: создать три history entries: старую важную, старую обычную и новую
обычную. При малом бюджете должна удалиться старая обычная, а report должен
объяснить решение.

## Проверка

Запускайте тесты из корня репозитория:

```bash
go test ./...
```

После выполнения задачи проверьте:

- какие фрагменты попали в запрос модели;
- какие observations попали в историю;
- что было обрезано, суммаризировано или удалено;
- почему итоговый запрос поместился или не поместился в бюджет.
