# Лабораторные работы: 04-Agents-Skills

Эта ветка тренирует навыки агента (`Agent Skills`) как механизм расширения
харнесса. Локальный `SKILL.md` не добавляет новый инструмент, но меняет
контекст, рабочие инструкции и поведение модели в `run`.

Ключевая архитектурная граница ветки — пакет `internal/skills` и его стыки с
`internal/agentcontext`, `internal/tools` и `internal/agent`. Skill не должен
становиться плагином кода: он раскрывает workflow и ресурсы, а реальные
действия всё равно идут через обычные инструменты и общую policy.

## Базовый уровень

### 1. Улучшить диагностику поиска и явного выбора навыка

Контекст проблемы: loader уже пропускает невалидные `SKILL.md`, а неизвестный
явный выбор завершает `run` до обращения к модели. Но пользователю важно быстро
понять, сломан ли сам frontmatter, отсутствует ли skill или в задаче просто
ошибка в маркере.

Индустриальный ориентир: discovery расширений должен быть отказоустойчивым.
Ошибка одного расширения не ломает весь каталог, а диагностика показывает путь,
причину и следующий безопасный шаг.

Задание: расширьте диагностику `internal/skills`: ошибки frontmatter должны
показывать путь, поле или строку, причину и короткую подсказку. Ошибка
неизвестного `@skill:name` должна показывать неизвестное имя, доступные skills и
предложение проверить `skills list` или `skills validate`.

Запишите в trace событие явного выбора, например `skills_explicit_selection`,
где видны найденные и неизвестные имена. При корректном явном выборе
автоматическая активация остаётся отключённой: catalog не добавляется, а
`activate_skill` не выдаётся модели.

Ограничения:

- невалидный skill не должен попадать в catalog;
- ошибка одного `SKILL.md` не должна ломать поиск остальных;
- при неизвестном явно выбранном skill модель не должна вызываться;
- не раскрывать полный текст `SKILL.md` в ошибке или trace;
- не добавлять YAML-библиотеку или другие зависимости;
- сохранить поддержку `@skill:name`, `@skill/name`, `$name` и фраз.

Критерий готовности: по `skills validate`, ошибке CLI и trace понятно, где
именно проблема: файл skill, отсутствующее имя или пользовательский маркер.

Проверка: создать валидный skill, несколько сломанных `SKILL.md` и запуск
`runWithClient("@skill:missing ...")`. Проверить ошибки, отсутствие model call
при неизвестном skill и событие явного выбора в trace.

### 2. Добавить предварительный просмотр активации навыка

Контекст проблемы: сейчас `skills show <name>` показывает metadata, ресурсы и
инструкции, но не отвечает напрямую, какой durable-фрагмент получит модель после
активации.

Индустриальный ориентир: у расширений полезен dry-run режим. Он не выполняет
агентский цикл, но показывает эффект на системный контекст и помогает автору
skill проверить упаковку инструкций.

Задание: добавьте команду вроде
`go run ./cmd/madharness-mini skills preview <name>`. Она должна без вызова
модели показать обёртку активированного skill: заголовок, путь к `SKILL.md`,
корневой каталог, описание, служебные поля, `allowed-tools`, список bundled
resources и id закреплённого фрагмента `skill:<name>`.

Ограничения:

- команда не должна обращаться к модели;
- команда не должна активировать skill в реальном `run`;
- не читать содержимое resources автоматически;
- не показывать файлы за пределами каталога skill.

Критерий готовности: пользователь заранее видит, что изменится в системном
контексте после `activate_skill`.

Проверка: создать skill со служебными полями, `allowed-tools` и ресурсами.
Проверить вывод preview: в нём есть wrapper и список ресурсов, но нет содержимого
файлов из `references/` или `scripts/`.

## Основной уровень

### 3. Ограничить размер каталога навыков для модели

Контекст проблемы: compact catalog входит в первый model call режима `run`.
При большом числе skills или длинных descriptions catalog может занять
существенную часть бюджета ещё до вызова инструмента.

Индустриальный ориентир: progressive disclosure должно иметь бюджет. Модель
видит достаточно информации для выбора skill, но не получает весь каталог без
лимита.

Задание: добавьте ограничение на длину description одного skill и общий размер
catalog-фрагмента. Если catalog обрезан, он должен явно сообщать модели, сколько
skills показано и сколько скрыто из-за лимита.

В `context_report` или trace должно быть видно, сколько skills попало в catalog,
сколько было скрыто и сколько символов занял catalog.

Ограничения:

- полный текст `SKILL.md` не должен попадать в catalog;
- явная активация skill должна работать без catalog;
- enum `activate_skill.name` должен включать все валидные skills, даже если
  часть catalog скрыта;
- не добавлять tokenizer или внешние зависимости.

Критерий готовности: catalog остаётся полезным для выбора skill, но не раздувает
первый запрос к модели.

Проверка: создать несколько skills с длинными descriptions, собрать первый
`messages` в `run` и проверить, что catalog ограничен, помечен как обрезанный, а
`activate_skill` всё ещё знает все имена.

### 4. Проверить файлы, на которые ссылается `SKILL.md`

Контекст проблемы: `SKILL.md` задаёт маршрутизацию ресурсов, но harness пока
только перечисляет файлы рядом с ним. Автор skill может случайно сослаться на
несуществующий reference или забыть описать важный script.

Индустриальный ориентир: пакет расширения должен иметь диагностику целостности.
Harness не решает за автора порядок чтения файлов, но показывает фактическое
состояние пакета.

Задание: добавьте диагностику ресурсов skill. При `skills show <name>` и после
`activate_skill` harness должен показывать:

- какие файлы из `references/`, `scripts/` и `assets/` лежат рядом со
  `SKILL.md`;
- какие из них упомянуты в тексте `SKILL.md`;
- какие упомянуты, но отсутствуют;
- какие существуют, но никак не описаны.

Для упоминаний достаточно простого поиска относительных путей в тексте
`SKILL.md`. Если файлов слишком много, список должен быть обрезан и явно
помечен флагом `resources_truncated`.

Ограничения:

- `SKILL.md` остаётся единственным источником маршрутизации;
- не читать содержимое ресурсов автоматически;
- не включать бинарные файлы в контекст модели;
- не перечислять файлы за пределами каталога skill;
- не считать диагностику использованием ресурса;
- сохранять событие `skill_resource_used` только при реальном чтении или запуске
  файла skill.

Критерий готовности: по `skills show` и ответу `activate_skill` видно, что у
skill есть все файлы, на которые ссылается `SKILL.md`, а лишние или отсутствующие
файлы легко заметить без чтения их содержимого.

Проверка: создать skill с `references/style.md`, `scripts/check.py`,
`assets/logo.png`, одним отсутствующим файлом в тексте и одним лишним файлом на
диске. Проверить вывод `skills show`, response `activate_skill`, флаг
`resources_truncated` на большом наборе файлов и отсутствие содержимого ресурсов
в первом сообщении для модели.

## Продвинутый уровень

### 5. Сделать `allowed-tools` реально проверяемым

Контекст проблемы: `allowed-tools` читается из frontmatter и попадает в wrapper
активации как экспериментальная подсказка. Такая подсказка не является
политикой, поэтому пользователь может неверно ожидать реального ограничения
инструментов.

Индустриальный ориентир: capability policy должна быть либо исполняемой, либо
явно диагностированной как advisory. Неочевидные обещания в metadata опасны для
безопасности и отладки.

Задание: выберите и реализуйте строгую семантику `allowed-tools`: либо активный
skill ограничивает инструменты, которые модель видит в следующих ходах, либо
harness явно диагностирует, что поле пока не применяется как ограничение.

Если выбираете реальное ограничение tools, определите поведение для нескольких
активных skills: объединение разрешённых tools, пересечение или приоритет
последнего активированного skill. Это решение должно быть видно в документации
и trace.

Ограничения:

- глобальная `Policy` остаётся сильнее любого skill;
- skills без `allowed-tools` не должны ломаться;
- отказ должен быть обычным observation `ok=false`, если модель всё же вызывает
  запрещённый tool;
- не добавлять hooks, субагентов или MCP.

Критерий готовности: по trace, документации и поведению понятно, ограничивает ли
`allowed-tools` инструменты и как именно.

Проверка: создать skill с `allowed-tools: read_file search_code`, активировать
его и проверить, что `write_file` или `run_shell` либо исчезают из tool schemas,
либо дают понятную диагностику выбранной advisory-семантики.

### 6. Задать порядок приоритета нескольких активных навыков

Контекст проблемы: каждый активный skill добавляется как durable fragment
`skill:<name>`. При нескольких skills порядок системных инструкций должен быть
предсказуемым, особенно если workflow конфликтуют.

Индустриальный ориентир: конфликтующие инструкции расширений не стоит
«понимать» автоматически. Harness должен задавать стабильный порядок, показать
источник активации и дать модели короткую подсказку, как активировать несколько
skills.

Задание: спроектируйте явную семантику приоритета нескольких active skills.
Вариант: явно выбранные skills применяются в порядке упоминания в задаче, а
skills, которые модель подключает сама через `activate_skill`, добавляются после
них в порядке активации.

В `context_report` и trace нужно показать список активных skills, источник
активации (`explicit` или `tool`), порядковый номер и итоговое место фрагмента в
system context.

Ограничения:

- повторная активация того же skill не должна дублировать fragment;
- порядок должен быть стабильным и покрытым тестом;
- не менять смысл `AGENTS.md` и базового system prompt;
- подсказка для модели должна быть короткой и не раздувать catalog;
- при конфликте harness не анализирует markdown-текст `SKILL.md`: приоритет
  задаётся только порядком.

Критерий готовности: по `context_report` можно понять, какие skills активны и в
каком порядке их инструкции попали в system context, а модель получает явную
подсказку о значимости порядка нескольких вызовов `activate_skill`.

Проверка: создать два skills с конфликтующими инструкциями. Сначала
активировать их явными маркерами пользователя и проверить порядок fragments.
Затем дать задачу без явных маркеров, где fake model вызывает `activate_skill`
для обоих skills, и проверить порядок в `messages`, `context_report` и trace.

## Проверка

Запускайте тесты из корня репозитория:

```bash
go test ./...
```

Полезные ручные проверки:

```bash
go run ./cmd/madharness-mini skills list
go run ./cmd/madharness-mini skills show <name>
go run ./cmd/madharness-mini skills validate
```

После выполнения задачи проверьте:

- какой текст skill добавил в durable context;
- не попал ли полный `SKILL.md` в trace;
- как модель узнаёт о доступных skills;
- сохраняются ли общие правила policy рабочей области.
